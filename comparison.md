# Rule DSL: library comparison

One column per library, scored on the criteria in `task.md`. Each cell says who does the work:

- **library:** the library does it out of the box;
- **adapter:** our code in `ui/src/parsers/<library>/` does it around the library;
- **both:** the library provides a piece, and our code builds on it.

Adapter work is code we maintain, and it can make a library look better than it is. Read each row together with its marker.

Bench numbers come from one `npm run bench` run on one laptop. Compare libraries within the same run only.

| Criterion | Ohm 17.5 | Lezer 1.4 |
| --- | --- | --- |
| **Conformance** | All 30 checks pass: Examples, scenario tokens and every `fixtures/*.parse.json`. | All 30 checks pass: Examples, scenario tokens and every `fixtures/*.parse.json`. |
| **Exact spans** | **library.** Every CST node carries its source interval. The adapter only adds the line offset, because each line is matched as its own string. | **library.** Every tree node carries its offsets into the whole text. The whole text is parsed at once, so nothing is shifted. |
| **Expected tokens** | **both.** Ohm reports the rightmost failures. Each token rule has its token name as its description (`before (BEFORE) = ...`), so the failures read as token names. The adapter keeps only token names, maps "end of input" to `SEP`, and reverses the list, since Ohm returns failures last-tried first. The method it reads, `getRightmostFailures`, exists at runtime but is not in Ohm's public types. | **adapter.** Lezer has no list of expected tokens: it recovers silently, and its parse state (`Stack.canShift`) is public only inside external tokenizers. The adapter probes instead. It appends a sample of each token to the statement up to the error and parses that in strict mode, so one error costs 26 extra parses. The order of the list is kept by hand (`TOKEN_NAMES`). At the start of the first line the list also has `SEQUENCE` and `SEP`, which Ohm leaves out. |
| **Error recovery** | **adapter.** Ohm stops at the first failure and returns no partial CST. The adapter splits the text at `SEP` tokens and matches each line on its own, so a bad line is dropped and the lines after it still parse. A second grammar rule (`LineHeader`) recovers the header of a line whose statement failed. | **both.** Lezer parses the whole text, recovers on its own and always returns a full tree, with error nodes where it skipped or inserted tokens. The adapter drops every statement that holds an error node, reports the first error of each line and keeps the header of a failed line. On 8 broken inputs tried by hand, it gave the same commands and diagnostics as Ohm, apart from the first-line case above. |
| **Lex errors** | **both.** The grammar has an `unknown` rule that catches any word no token matches, so tokenizing never fails. The adapter turns those words into `lex` diagnostics, and attaches the expected tokens when the parse fails at the same spot. | **both.** Keywords are specializations of one `Word` token. A `Word` the grammar never takes, or a character no token matches, ends up in the tree, and the adapter turns it into a `lex` diagnostic. Lezer's tokenizer puts precedence before length, so `3xy` lexes as `COUNT` plus the unknown word `y`; Ohm reports `3xy` as one unknown word. |
| **Two modes** | **adapter.** The adapter checks whether the first token is `SEQUENCE` and picks the start rule for every line (`SequenceStart`, then `Slot`, or `Line`). The grammar could decide this itself, but per-line matching for recovery rules that out. | **library.** `@top Program { SequenceText \| RulesText }`: the parser picks the mode from the first token, and the adapter reads the name of the top node. |
| **Header blocks** | **adapter.** The grammar parses a header and a statement on one line. Which subject or anchor block a line belongs to is tracked by the adapter, because lines are matched apart. The same goes for the placement and anchor-block checks. | **adapter.** As with Ohm, lines are flat siblings in the tree, and the adapter tracks the block and runs the placement and anchor-block checks. Nesting statements under their header needs two tokens of lookahead (`ACTIVITY`, then `COLON`) to see where a block ends, and LR(1) has one. Lezer's GLR markers could get around it; not tried. |
| **Adapter share** | Grammar 98 lines. Semantics, which build the commands, 200 lines. Driver, which handles lexing, line splitting, recovery, mode, blocks and checks, 115 lines. The tokenizer runs once more inside `parse`, to split the lines. | Grammar 88 lines. Semantics 114 lines. Driver, which handles lexing, line splitting, error reporting, the expected-token probe, blocks and checks, 136 lines. Lines come from the `SEP` nodes in the tree, so there is no second tokenizer pass. Build setup: the Vite plugin and a `*.grammar` module declaration. |
| **Adding a rule** | Counted in the code, not tried: 6 places in 2 files. In `grammar.ohm`: the keyword rule, the `token` list and the statement rule plus its `Rule` alternative. In `index.ts`: one semantic action and `TOKEN_NAMES`. On top of that, the shared `Command` type, and `npm run generate:ohm` to rebuild the bundle (a test fails until it is rebuilt). | Counted in the code, not tried: 7 places in 2 files. In `rules.grammar`: the keyword rule, the `token` list and the statement rule plus its `Statement` alternative. In `index.ts`: a case in `rule()`, `TOKEN_NAMES` and `SAMPLE`. On top of that, the shared `Command` type. |
| **Types** | **both.** Command types are written by hand. `@ohm-js/cli` generates the action-dictionary types next to the bundle, so a misspelled action name or an extra argument is a type error, and each argument gets its node kind (`NonterminalNode`, `IterationNode`, `TerminalNode`). A missing argument still passes, and operation results are `any`. | **adapter.** Command types are written by hand. The tree is untyped: children are looked up by name (`getChild('DURATION')!`), so a typo in a node name compiles and fails at runtime. The generator can emit term IDs, not node types. |
| **Runtime: bundle** | about 96 KB minified, about 25 KB gzip (`ohm.min.js`). The grammar ships precompiled as a recipe (`grammar.ohm-bundle.js`, 24 KB unminified), so startup skips parsing the grammar text. | About 71 KB minified, about 21 KB gzip for `@lezer/lr`, `@lezer/common`, the parse tables and the adapter (Vite build of `lezer/index.ts`). The same build of the Ohm adapter is about 135 KB and 31 KB. `@lezer/generator` compiles the grammar at build time through a Vite plugin and is a dev dependency only. |
| **Runtime: 200 lines** | Rules text: tokenize 10.9 ms, parse 19.7 ms. Sequence text: tokenize 6.5 ms, parse 11.1 ms. | Rules text: tokenize 0.99 ms, parse 0.91 ms. Sequence text: tokenize 0.56 ms, parse 0.37 ms. |
| **Maintenance** | 17.5.0 is the latest stable version (March 2026). 18.0 is in beta (beta.10, March 2026). | `@lezer/lr` 1.4.11 (October 2026), `@lezer/generator` 1.8.1 (September 2026). Part of CodeMirror 6 and maintained by its author. The repo installs 1.4.10, because npm here holds back releases younger than about 3 days. |
| **Editor support** | **both.** The same grammar gives token types for highlighting, and expected tokens at the cursor for completion. Ohm also supports incremental re-matching after an edit (`Matcher.replaceInputRange`); not tried. | **library.** Lezer is the parser behind CodeMirror 6: incremental re-parsing, highlighting from the same grammar (`styleTags`), and the tree at the cursor for completion. Expected tokens for completion would go through the same probe. `RuleEditor` is not a CodeMirror editor today; not tried. |
